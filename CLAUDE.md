# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Linux desktop app (Electron + React + TypeScript) that **watches Etsy shops** through the **official Etsy Open API v3**. You paste links to Etsy shops; the app reads every active listing of each shop — **everything the API returns** (content, popularity: views / favorers / featured rank, images, videos, personalization; the full JSON is kept too) — stores it in a local SQLite database, copies listing photos into a local **MinIO** bucket (`docker-compose.yml`), and on every rescan ("Сканувати повторно") tells you which listings are **new since the previous scan** — plus which disappeared, came back, or changed (and *what* changed: price, title, description, photos, tags, …), and how popularity grew. It also keeps **every review of each watched shop** (GET /shops/{id}/reviews — the best available proxy for "how often a listing sells", since Etsy doesn't expose other shops' per-listing sales): per-listing review count and average rating, "+N нових відгуків" since the last scan, review photos copied to MinIO. It also asks Etsy for the **buyer-facing price** for one buyer country (Settings → "Країна покупця", default UA: VAT, UK shipping, active promotions — what the shop page shows, vs. the seller's base price the API's `price` is), shows it like the site ("1,20 USD ~~3,00 USD~~ −60%" — `Intl` uk-UA prints the currency code, only UAH gets ₴) and tracks **promotions** across scans. The user's own Etsy API key (keystring + shared secret) is entered in the app's Settings. The UI language is Ukrainian; code and comments are English. A local **MCP server** named `etsy-tracker` (the server button at the top of the sidebar; off by default) lets any Claude — Claude Code, Claude Desktop, other MCP clients — read all of it, use live Etsy reads and, for the user's own shop and only with the "allow changes" switch, change it (see "MCP server"). "✏️ Мій магазин" signs in to Etsy (**OAuth 2.0 + PKCE**) to **edit the user's own shop**: listings of any state (title, description, tags, materials, auto-renew, activate/deactivate), the shop texts, and **new listings** through drafts kept in the app (draft → photos → digital files → publish; a sent draft stays linked to its Etsy listing — edit it and "Оновити на Etsy" updates that listing; drafts made on etsy.com are pulled in after each scan of the own shop; a draft can be deleted in the app or on Etsy too — see "Drafts in the app"). Once signed in, the own shop is tracked like any other and marked "мій" (see "Own shop (OAuth)"). Any stored listing can carry the user's own **mark** — "В роботі" / "Реалізовано" ("we already made our version of this example"), with a note and our listing / draft — set in the app or by Claude over MCP, shown on cards, filterable and sortable (see "Listing marks").

## Commands

```bash
npm install          # Node ≥ 22.13 (node:sqlite unflagged); no native modules — nothing to rebuild for Electron
npm run dev          # run in dev (electron-vite, HMR for renderer)
npm run typecheck    # tsc --noEmit over tsconfig.node.json + tsconfig.web.json
npm run build        # typecheck, then build main/preload/renderer into out/
npm run dist         # build then package AppImage + deb (electron-builder, Linux)
npm test             # run the Vitest suite (shared + main + renderer)
bash scripts/install-desktop.sh   # register dist/*.AppImage as a menu app with icon
docker compose up -d # the MinIO image store (S3 API 127.0.0.1:9100, console http://127.0.0.1:9101)
```

Correctness gates: `npm test` (Vitest) for behaviour and `npm run build` for types — `build` runs `tsc --noEmit` on both tsconfigs **before** electron-vite, because electron-vite/esbuild and Vitest never typecheck. `tests/` is not typechecked. No linter or formatter is configured.

**Rebuilding the installed app (only when asked).** If the user runs the app from the installed application-menu icon, that runs the packaged `dist/etsy-tracker-<version>.AppImage` — `npm run build` alone only refreshes `out/`. To get a change into the installed app, run the `rebuild-and-restart-app` skill (`npm run dist` → `bash scripts/install-desktop.sh` → kill + relaunch). Do this only when the user asks. See `.claude/skills/rebuild-and-restart-app` for the exact steps and Linux gotchas (pkill self-match, sandbox can't signal the GUI app, stale SingletonLock). Before any commit, follow `.claude/skills/verify-before-commit`.

Sandbox note: inside the Claude Code tool sandbox Electron can't use Chromium's SUID sandbox or the GPU; for a smoke run use `npx electron-vite dev --noSandbox -- --disable-gpu`. The user's own `npm run dev` works without those flags. A smoke run opens the user's real `~/.config/etsy-tracker` DB and **migrates** it; to avoid that, point it at a copy: `XDG_CONFIG_HOME=<scratch>/cfg npx electron out/main/index.js --no-sandbox --disable-gpu` (Electron's `appData` follows `XDG_CONFIG_HOME`).

## Architecture

Three Electron processes, each a separate electron-vite build target (`electron.vite.config.ts`). Types shared via `src/shared/types.ts`; the renderer imports `src/shared/*` through the `@shared` alias (main/preload use relative `../shared/...`).

- **main** (`src/main/`) — Node side. Owns the database, the API key, and **all** Etsy traffic. Pure functions per concern, wired together in `ipc.ts`:
  - `db.ts` — `node:sqlite` schema, migrations, row mapping, queries. Every function takes the `Db` handle.
  - `etsyApi.ts` — the HTTP client (`createEtsyClient`), errors, quota/Retry-After parsing.
  - `mapEtsy.ts` — Etsy JSON → our records (`mapListing(page, details, currency, includes, buyer)`, `mapListingDetails`, `mapImage(s)`, `mapVideos`, `mapPersonalization`, `mapMoney`, `mapBuyerPrice`, `buyerPriceOf`, `mapShop` + `mapShopProfile`, `listingStats`, `shopStats`, `mapReview` + `reviewKey`).
  - `promotions.ts` — the pure promotion decision per listing per scan (`promotionStep`, `samePromotion`, `countsAsStart`/`countsAsEnd`); see "Buyer prices & promotions".
  - `reviewSync.ts` — `createReviewSyncer`: the per-shop, resumable, budgeted review sync (backfill + incremental), `pageStep` (offset paging that survives a shrinking window), `reviewErrorMessage`.
  - `scanner.ts` — scan orchestration + the pure diff (`diffListings`, `trackedDiff`, `applyScan`).
  - `imageStore.ts` — the `ImageStore` interface (ensureBucket/ping/put/stat/get/remove), the MinIO implementation (`createMinioImageStore`, official `minio` npm client), object keys, Ukrainian error texts.
  - `imageSync.ts` — `createImageSyncer`: the background Etsy CDN → MinIO copier for listing images **and review photos** (`downloadImage` with timeout/retry).

### Database (`src/main/db.ts`)

Built-in **`node:sqlite`** (`DatabaseSync`) — works in Electron 38 and in system Node 22, so there are no native modules and tests use a real SQLite (`openDb(':memory:')`). The module is loaded lazily via `process.getBuiltinModule('node:sqlite')` inside `loadSqlite()`, which temporarily wraps `process.emitWarning` to swallow only the one-time "SQLite is an experimental feature" ExperimentalWarning (a top-level import would be hoisted above any filter in the CJS bundle). Only `import type` from `node:sqlite` elsewhere.

File: `<userData>/etsy-tracker.db` (WAL, `foreign_keys = ON`). `userData` is pinned in `index.ts` to `~/.config/etsy-tracker` (same for dev and packaged builds, independent of productName). `index.ts` also pins `app.setName('etsy-tracker')` (package.json has no `productName`, and electron-builder's `productName` is not written into the packaged package.json): Linux safeStorage names its keyring secret after the app name and X11 uses it as WM_CLASS, which `scripts/install-desktop.sh` matches with `StartupWMClass=etsy-tracker`.

**Migrations:** `MIGRATIONS` is an append-only array of SQL strings; `PRAGMA user_version` holds how many have run. `migrate(db, migrations = MIGRATIONS)` applies each pending one in its own transaction (a failing one rolls back and leaves `user_version` unchanged — tested with an injected list) and refuses a db whose version is newer than the app knows — so once a v2 build has opened the user's DB, an older installed AppImage refuses it ("створена новішою версією") until it is rebuilt. Never edit a shipped entry — add a new one (and a test in `tests/main/db.test.ts`, starting from a real database at the previous version).

Schema (v8 = `MIGRATIONS.length`; v1–v5 already ran on the user's real DB (v5 with the drafts build); v6 + v7 = linked drafts, shipped next with the linked-drafts build; v8 = listing marks — treat them all as shipped: never edit v1–v8, append v9):

- `reviews` (v3) — one row per Etsy `TransactionReview` from GET /shops/{id}/reviews: `id` (our autoincrement id — `etsyimg://review/{id}/fullxfull`), `review_key` UNIQUE (natural key, see below), `shop_id` (FK cascade), `listing_id` (no FK: reviews of listings we never stored are kept too), **every OAS field** — `transaction_id`, `buyer_user_id`, `rating`, `review` (entities decoded), `language`, `image_url_fullxfull` (NULL unless an https etsystatic URL), `create_timestamp`/`created_timestamp`/`update_timestamp`/`updated_timestamp` (the OAS has both spellings; seconds) — plus `raw_json` (the latest API object), `first_seen_at`/`last_seen_at`/`changed_at` (ms; `changed_at` = last time a sync saw an edit), `first_seen_scan_id` (FK `scans` SET NULL — the scan whose sync inserted it), `origin` `backfill|new`, and the photo's MinIO state `image_sync_status` (`pending|stored|error`, NULL = no photo), `image_sync_error`, `image_sync_attempts`, `image_stored_at`, `image_key`, `image_byte_size`, `image_content_type`, `image_etag`, `image_sha256`. Indexes: `(listing_id)`, `(shop_id, created_timestamp)`, `(first_seen_scan_id, origin)`, `(shop_id, image_sync_status)`. **Natural key:** the shop endpoint returns `TransactionReview`s and a transaction is reviewed at most once → `t-{transaction_id}`; should `transaction_id` ever be missing, the deterministic fallback is `x-{listing_id}-{buyer_user_id|0}-{created_timestamp}` (`reviewKey`; only `[a-z0-9-]`, so it is a MinIO path segment as is; two hidden-buyer reviews of one listing in the same second would collide — accepted).
- `review_sync` (v3) — one row per shop, the sync cursor: `backfill_complete`, `backfill_upper` (s; the backfill covers `created ≤` this, fixed at its start), `total_estimate` (Etsy's `count` at that start — the "~9 300"), the current backfill window `win_hi`/`win_lo` (NULL = open downwards)/`win_offset`/`win_count`/`win_span`, `synced_through` (s; incremental passes covered up to here), an incremental pass in progress `inc_lo`/`inc_hi`/`inc_target`/`inc_offset`/`inc_count`, `oldest_created`/`newest_created`, `requests_total`, `last_run_requests`, `last_synced_at` (ms), `last_error`.
- `listing_review_stats` (v3) — `(scan_id, listing_id)` PK: `review_count`, `review_avg`, `new_count`, `complete` (0 = the backfill was incomplete → a lower bound), one row per **active** listing (0 included) per successful scan, written when that scan's review sync finishes (a manual sync re-writes the latest scan's rows). `shop_review_stats` (v3) — `scan_id` PK: `review_count`, `review_avg`, `new_count`, `complete`, `synced_at`. Both cascade with `scans`; `listListingStats` LEFT JOINs the listing one (`reviewCount`/`reviewAvg`/`reviewsComplete` in `ListingStatsPoint`).

`upsertListing` with `buyerPrice: undefined` keeps the stored buyer price, `null` clears it, an object replaces it (see `buyerPriceOf`). `upsertListing` with `images: null` / `videos: null` keeps the stored ones (the details call didn't answer for that listing); an array is synced into `listing_images`/`listing_videos` (`syncListingImages`: new id → `pending`; known id → metadata refreshed, a changed `url_fullxfull`/`url_570xN` resets it to `pending`; missing id → `removed_at`; a returning id is revived). `skus` and `details_fetched_at` are only overwritten when `detailsFetched`; `personalization` only when `personalizationFetched` (defaults to `detailsFetched`; `mapListing` sets it only when the details object has the key or `Personalization` was among `client.detailIncludes()` — after the Images-only fallback the stored questions are kept and not diffed); `views` is `COALESCE`d (null = unknown → keep); `raw_json` from details replaces the stored one, a page-only object never does. `deleteShop` removes the shop's listings, images, videos, scans, stats and changes in one transaction — reviews, `review_sync` and the review stats go by FK cascade (MinIO objects: collect `listShopObjectKeys` first — it includes the review photo keys; `shop:remove` does, then `images.removeObjects`). Review queries: `upsertReviews`, `reviewTotals`, `countReviewsCreated(shop, lo, hi)` (a finished sync window's check), `writeReviewStats` (no-op while never synced), `reviewSyncInfo` (→ `ShopSummary.reviews`; null = no run finished yet, `synced: false` = only failed runs), `getReviewSync`/`saveReviewSync`/`sameReviewSync`, `listListingReviews` (paged, newest first; a NaN/negative offset is 0, a huge/infinite one an empty page), `listNewReviews(scanId, limit = 200)` (with the listing's title + first image id; capped — the real count is `ReviewSyncInfo.newCount`), and per-listing aggregates in `listActiveListings`/`getListing` (`Listing.reviewCount`/`reviewAvg`/`reviewsNew`/`reviewsPartial`; all null/false while the shop was never synced, i.e. no `review_sync.backfill_upper` — which a run sets only together with its first stored page, so a first run answered 403/404 leaves it NULL).

### Etsy API client (`src/main/etsyApi.ts`)

- Base `https://openapi.etsy.com`, paths `/v3/application/...`. Header on **every** request: `x-api-key: <keystring>:<shared_secret>` — since 2026-02-09 Etsy rejects the keystring alone, so the app asks for both halves (`composeApiKey` in `settings.ts`). No OAuth: only public endpoints are used.
- Endpoints: `GET /openapi-ping` (key check → `{application_id}`), `GET /shops?shop_name=&limit=100[&offset=]` (findShops — a name *search*, may be fuzzy, so we keep only an exact case-insensitive `shop_name` match and page on, up to `FIND_SHOP_MAX_PAGES` = 5, while it isn't found and `count` says there is more; no match is `count: 0`, not 404), `GET /shops/{id}`, `GET /shops/{id}/listings/active` (paginated, **no `includes`** → no images), `GET /listings/batch?listing_ids=1,2,3&includes=Images,Videos,Personalization[,BuyerPrice&buyer_country=UA]` (≤100 ids, comma-separated, no brackets), `GET /listings/{id}?includes=…[&buyer_country=]` (`getListing`, null on 404), `GET /shops/{id}/reviews?limit=100[&offset=][&min_created=][&max_created=]` (`getShopReviews`, getReviewsByShop → `TransactionReviews`; bounds clamped to the OAS minimum 946684800; the OAS documents **no result order** and no offset cap of its own — the global v3 12000 applies). `includes` (`DETAIL_INCLUDES`): the OAS enum is Images, Shop, User, Translations, Videos, Personalization, BuyerPrice — Shop/User duplicate what we read, Translations multiply the payload, so they aren't requested. **BuyerPrice** is added (with `buyer_country`, OAS: "ISO 3166-1 alpha-2 … used for buyer-facing price calculations (VAT, inclusive shipping). Does not filter listings") when the caller passes `DetailOptions.buyerCountry` (`getListingsByIds(ids, onChunk, {buyerCountry})`, `getListing(id, {buyerCountry})`) — same requests, no extra ones. The OAS documents `buyer_country` only on /listings/batch and says `buyer_price` is "currently only supported on the /listings/batch endpoint"; we send both on the single GET too (the bisect fallback) and treat a missing `buyer_price` key there as "not learned" (keep the stored one). Include step-down (`withIncludes`, each step tried once): (1) a 400/401/403 while BuyerPrice is in the set and not yet proven **for that buyer country** on a batch (or on a single GET at all) → the same set without BuyerPrice; success on a batch = BuyerPrice refused for that country for the client's life (`buyerPriceRefused(country)`; per country — a country Etsy rejects doesn't switch buyer prices off for the next one; a single GET never decides it); (2) a 401/403 → `Images` only for the rest of its life (`detailIncludes()` — never contains BuyerPrice): first `Images,BuyerPrice` (when a country is asked — success proves BuyerPrice), then, only while BuyerPrice is unproven, `Images` alone, which refuses BuyerPrice (batch only) — so a refused Videos/Personalization never costs the buyer prices; anything else, or every step failing, throws the original error, so a 400/404 for an unknown id still bisects (an unproven BuyerPrice costs one extra try per failing chunk in that path; once a batch proved it, none). So no include that needs OAuth can ever break scans. `views` is documented only in `ShopListingWithAssociations` (Etsy tabulates it once a day), but live the `/listings/active` page items carry it too (same value; also `skus`, `production_partners`) — `mapListing` falls back to the page's `views` when details didn't answer. Details are still fetched for every listing for images/videos/personalization. Never `GET /shops/{id}/listings` — it needs OAuth `listings_r`.
- **Batch 404s:** the OAS documents a 404 for `/listings/batch` (likely when an id is unknown — deleted / no longer public; unverified live). `getListingsByIds` therefore bisects a chunk answered 404 or 400 down to single `GET /listings/{id}` calls; a single-id 404 means "gone" (left out of the result), any other error still throws. Without this, a deleted listing would make every rescan of its shop fail forever.
- **Own-shop calls (OAuth)** — `call(path, {method, query, form, oauth, apiKey})` is the one request path (`request` = a GET through it). `oauth: true` adds `Authorization: Bearer <token>` from `getAccessToken()` (the x-api-key is still sent); no token → `not_signed_in` without a request; a 401 → `refreshAccessToken()` once and the call retried (an explicit `oauth: '<token>'` is never refreshed); still 401 → `oauth` "Вхід в Etsy більше не дійсний — увійдіть ще раз", 403 → `forbidden` (never the "bad API key" text). `form` bodies are `application/x-www-form-urlencoded` (`formBody`: arrays comma-separated like Etsy's examples, booleans `true/false`). PATCH/PUT are retried like GETs (idempotent); **POST is never retried** on 5xx/network/timeout (it could create twice). `multipart` bodies (FormData; fetch sets the boundary) for uploads. Methods: `getMe(token?)` (GET /users/me, `shops_r` → `{user_id, shop_id}`), `getShopListingsByState(shopId, state, offset)` (GET /shops/{id}/listings?state=&includes=Images — any state, `listings_r`), `updateListing` (PATCH /shops/{id}/listings/{id}, `listings_w`), `updateShop` (PUT /shops/{id}, `shops_w`), `createDraftListing` (POST form), `uploadListingImage` (multipart `image` + `rank`), `uploadListingFile` (multipart `file` + `name` + `rank`), `getSellerTaxonomy` (GET /seller-taxonomy/nodes, API key only), `getShippingProfiles`, `getProcessingProfiles` (GET /shops/{id}/readiness-state-definitions). Price/quantity live in `updateListingInventory` (JSON, every product/offering) — not implemented yet.
- Paging caps: `limit` ≤ 100, `offset` ≤ 12000 → at most ≈12,100 listings per shop. `getAllActiveListings` loops `offset += 100` until `offset >= count`, an empty page, or past the cap; dedupes by `listing_id`; sets `truncated` when `count > 12100`.
- Requests are serialized through one promise chain with a minimum gap (`minIntervalMs`, default 125 ms). 429 → wait `Retry-After` (seconds or HTTP date) + jitter, else exponential backoff; a `Retry-After` beyond `maxRetryAfterMs` (60 s — the daily quota) fails fast. 5xx and network errors → backoff retry. Up to `maxRetries` (4). Every attempt has a timeout (`requestTimeoutMs`, default 30 s, via `AbortController` covering headers and body); a timeout is retried at most `maxTimeoutRetries` (1) times, then fails as a `network` error "Etsy не відповідає (тайм-аут 30 с)…" — so a stalled connection can't block the serialized queue (ping, findShops, other scans) for minutes. 401/403 → `auth`, 404 → `not_found`, 400 → `bad_request`; each `EtsyApiError` carries a Ukrainian `message`, `kind`, `status`, Etsy's `{"error"}` text as `detail` and `x-etsy-request-uuid` as `requestId`.
- Quota: `x-limit-per-day`, `x-remaining-today`, `x-limit-per-second`, `x-remaining-this-second` are parsed from every response (`parseQuota`) and pushed to the renderer (`quota:changed`, shown in the sidebar footer). Limits are per key and are never hardcoded.
- `fetch`, `sleep`, `random`, `now` are injectable — tests run against a fake Etsy, never the network.
- Verified live (2026-10, real key, SimplyOrganizedPro): `Videos`/`Personalization` includes work with API-key-only auth; a listing without personalization has `personalization: {personalization_questions: []}`; the quota headers are `x-limit-per-day`/`x-remaining-today`/`x-limit-per-second`/`x-remaining-this-second`; batch/page/shop responses match the fixtures except extra live-only keys (`rich_description`; on pages `views`, `skus`, `production_partners`, `suggested_title`, `ecgt_*`) — kept in `raw_json`; `featured_rank` values seen: -1, 0, 1, 2, 3 (the UI shows ★ only for ≥ 1).
- UNVERIFIED API details are coded defensively: entity decoding of title/description/tags (`shared/html.ts`), fuzzy findShops, what `/listings/batch` does with unknown ids (skip vs 404), whether a Seller-App key can read other shops.

### Scan & diff semantics (`src/main/scanner.ts`)

`createScanner({db, client, now, onProgress}).scanShop(shopId)`:
1. Refuses if that shop is already scanning (`busy`), inserts a `running` scan row.
2. `getShop` (refreshes title/icon/count + the full profile and shop stats; a vanished shop → 404 error), then pages all active listings.
3. Fetches details via the batch endpoint for **every** active listing on every scan (images/videos/personalization exist only there). **Cost per scan ≈ 1 (getShop) + ⌈N/100⌉ (pages) + ⌈N/100⌉ (details) requests** (+ the removal re-check), i.e. ~2 requests per 100 listings — v1 skipped unchanged listings, v2 can't. A listing deleted between paging and this call (404) is still saved from its page data, keeping its stored images/views.
4. Listings stored as active but missing from the pages are **re-checked** through the batch endpoint (they may just have shifted between pages); only those not `state: 'active'` in this shop — or unknown to Etsy (404) — count as removed. When the set was `truncated`, removal detection (and this re-check) is skipped entirely and the scan row gets `truncated = 1` (UI warns "≈12 100").
5. One transaction (`applyScan`): update shop info + profile + raw JSON, promotions (`applyPromotions`, before the upserts), upsert every current listing (columns, buyer price, raw JSON, `listing_images`, `listing_videos`), mark removed ones, insert `scan_changes`, write `listing_stats` and `listing_price_stats` for every current listing and `shop_stats` (baseline included), finish the scan row `ok` with totals (+ buyer country/status, promotions started/ended).
6. **Not** part of the scan: copying images to MinIO and syncing reviews. After an ok scan, `ipc.ts` calls `startImageSync(ctx, shopId)` and `startReviewSync(ctx, shopId, scanId)` (both fire-and-forget) — see "Image store" and "Reviews" — and, for the signed-in own shop, `startDraftPull(ctx, shopId)` (pulls its Etsy drafts — see "Drafts in the app").

Buyer prices: `ScannerDeps.getBuyerCountry` (index.ts → the buyer-country store) is read **once per scan** before the details calls, so a Settings change mid-scan can't mix countries; it applies from the next scan. Mapping per listing (`buyerPriceOf` → `ListingInput.buyerPrice`): `buyer_price` present → the mapped object (or null for `buyer_price: null`); key absent → undefined (keep the stored one) while BuyerPrice is still being asked, else null (clear — refused, or no country, so a stored price would only go stale); no details answer → undefined. The scan row gets `buyer_country` and `buyer_prices`: `ok` only when at least one details answer of the scan carried the `buyer_price` key (or the shop has no active listings); `unavailable` when `client.buyerPriceRefused(country)`, or when Etsy accepted the include but left the key out everywhere / every chunk went through single GETs (the per-listing rule above still keeps the stored prices then — unknown ≠ none). The banner says "Etsy не віддав ціни для покупця … під час останнього сканування — де ціна для покупця невідома, показано базові ціни продавця".

Rules:
- **Baseline:** a shop's first successful scan (`!hasOkScan`) saves everything (and stats) but records no changes (`is_baseline = 1`, counts 0). UI: "Базове сканування: збережено N товарів".
- **added** = `listing_id` never seen before; **returned** = stored with `removed_at` and active again (its own kind — not counted as new, no NEW badge, shown in a separate "Повернулися" group); **removed** = active before, gone now; **changed** = content differs (`trackedDiff`):
  - always: title, price (by value: `a1*d2 != a2*d1`, or a currency change), description (old/new stored as ≤ 1000-char excerpts, `DESCRIPTION_EXCERPT`), tags (as a set);
  - images: the ordered list of active `listing_image_id`s (new/replaced/removed photo or a new order), only when this scan fetched images and the stored row had images (or v2 details);
  - only when the stored row already has v2 details (so the first v2 rescan of a v1 row can't flag everything): materials and styles (sets), `whoMade`, `whenMade`, `taxonomyId`, `shopSectionId`, `listingType`, `isPersonalizable`, `isCustomizable`, `hasVariations`, processing time (`processingMin`+`processingMax` together), weight/dimensions (one `dimensions` string), personalization questions (only a known previous value vs. a fresh answer — `personalizationFetched`), video ids;
  - **views 0:** the OAS says a `views` of 0 may mean "not yet tabulated / not active at tabulation / error"; `distrustZeroViews` turns a 0 for a listing whose stored views were > 0 into null (unknown → kept, no negative delta). A new listing's 0 is stored.
  - **never a change**: views, favorers, featured rank (popularity), `quantity` (stock moves with every sale) and the **buyer price** (VAT, promotions — it moves with every sale and with the buyer country) — they're recorded per scan in `listing_stats` / `listing_price_stats` instead (promotions in `promotions`). The seller's own `price` change is still a "ціна" change. A changed image URL with the same id isn't a content change either (it only resets that image to `pending`).
  - The row's `new_value` keys say what changed; `shared/changes.ts` maps them to groups/labels ("ціна, опис, фото").
- **Failure:** all Etsy API I/O happens before the transaction, so any error (network, 429 exhaustion, API error mid-pagination or mid-details) leaves listings, images and stats untouched and only marks the scan row `error` with the Ukrainian message. The shop summary then has `lastScan` (failed) ≠ `lastOkScan`, and the UI shows the error above the previous results.
- Scans left `running` by a crash are closed as `error` when the scanner is created (`failStaleRunningScans`).
- `scanAll` (ipc.ts) scans shops sequentially, starts the image and review syncs after each ok shop (not awaited — their requests share the client's serialized queue with the next shop's scan), and stops early on an API-key error.
- Progress events (`scan:progress`): `Сторінка 2/5`, `Деталі 100/430`, `Перевірка зниклих …`, `Збереження…`; `scan:state` brackets each scan.

### Buyer prices & promotions (`mapEtsy.ts`, `promotions.ts`, `scanner.ts` `applyPromotions`)

Why: `ShopListing.price` is the seller's **base price** — no VAT, no promotion (250/100 USD). The shop page shows a buyer the price for their country: base + VAT (UA 20 % → 3.00) minus an active promotion (−60 % → 1.20), and in the UK the display price includes shipping (DMCC). OAS `ListingBuyerPrice` (`includes=BuyerPrice` + `buyer_country`): `base_price` (VAT incl., pre-discount, no shipping), `shipping_cost` (nullable: free/unavailable), `is_free_shipping`, `original_price` (the display price; UK = base + shipping, else = base), `discounted_price` / `discount_amount` (nullable: no promotion), `discount_percentage` (int64, nullable: none or a fixed-amount promotion), `has_discount`, `discount_start_epoch`/`discount_end_epoch` (int64, nullable). Every Money has its own `currency_code`; we keep one currency per set. `mapBuyerPrice`: `hasDiscount` requires `has_discount === true` **and** a `discounted_price`.

Promotions: `applyPromotions` runs in the scan transaction **before** the upserts (it compares with the stored = previous buyer price) for every current listing whose buyer price this scan learned (unknown → nothing: a running promotion stays open until a scan that knows says otherwise). `promotionStep(open, prev, bp, {isNew})` (`isNew` = added **or returned** by this scan — a returned listing's stored price is from before it vanished):
- same promotion (`samePromotion`: the same `discount_start` **and** % when both have a start — an extended end date is the same sale, a new % at the same start is a new one, so each row keeps the terms it had — else the same % and end) → continue (terms, prices, country, last seen refreshed);
- another promotion → end `replaced` + start `seen`; no discount any more → end `ended`;
- a discount with no running row → start `seen`;
- **no previous observation** (`prev` null — baseline, the first v4 scan, after a refusal / `buyer_price: null` cleared it — or `isNew`): a discount is `running` (we don't know when it began), and a running promotion that is now gone or different ends `unknown` (+ start `running` for the new one) — it ended somewhere in the blind window, so neither side is reported;
- a listing **removed** by the scan: its running promotion ends `removed` (kept in the history as "товар зник з магазину", not reported). If it comes back, the step treats it as new (above).
- **Country switch**: the reference country is the previous observation's. A promotion with the same terms simply **continues** under the new country (% and dates don't depend on it; only the VAT-inclusive prices do). A start or end that coincides with a switch is recorded with kind/reason `country` — kept in the history ("після зміни країни" / "змінено країну покупця") but **not** reported as started/ended (it may be the VAT/country, not the seller).
- Only `seen` starts and `ended`/`replaced` ends count (`scans.promotions_started/ended`, `listScanPromotions` → the "Акції" group); `running`/`country` starts and `country`/`removed`/`unknown` ends are history only.

What the UI shows and sorts by (`shared/price.ts` `shownPrice`): the sale price while a promotion runs, else `original_price` (VAT incl.), else (no buyer price) the seller's base price. Price sorts use it too, so the grid order matches what the cards say (currencies are not converted — as before). "Найбільша знижка" sorts by `discountPercent` (Etsy's %, else derived for a fixed-amount discount; none/unknown last); "Зі знижкою" keeps `hasActiveDiscount` listings.

### Reviews (`src/main/reviewSync.ts`)

`createReviewSyncer({db, client, now, budget, overlapSec, windowCap, quotaReserve, getQuota, onState, onDone}).sync(shopId, {scanId})` — one run at a time per shop (a request made while one is queued is merged into it; one made while one runs queues one follow-up). The whole shop's reviews come from one endpoint (each review carries `listing_id`) — never one request per listing.

- **Decoupled from scans:** it runs after the scan transaction committed; any failure (403/404/429/network, a deleted shop) only lands in `review_sync.last_error` / the `reviews:progress` state, never in the scan. `reviewErrorMessage`: 401/403 → "Etsy не дозволяє читати відгуки цього магазину з цим ключем (HTTP 403). Товари скануються як і раніше.", 404 → "Відгуки цього магазину недоступні (HTTP 404)…", 429 → "…догрузяться під час наступної синхронізації", else "Відгуки: …". The next clean run clears the error.
- **Resumable:** every page is upserted together with the updated `review_sync` cursor in one transaction, so a crash/quit/error resumes exactly at the next page. Each page advances a **copy** of the cursor that becomes the run's cursor only after its transaction committed — a failed commit (any SQLite error) leaves the cursor before that page, and the run's final save writes that one. A first run that stored no page saves only the error/counters (`backfill_upper` stays NULL → "never synced").
- **Shop identity:** before every write the run checks it is still the shop it started on — the row exists with the same `added_at` and `review_sync` still holds exactly what this run last read or wrote (`sameReviewSync`). A shop deleted (and maybe added again — same Etsy id) mid-run ends the stale run as "Магазин видалено." without writing its cursor into the new shop's row.
- **Run order:** first the **incremental** pass (skipped on the very first run), then the **backfill** with what budget is left.
- **Backfill** (first time = the full history): `backfill_upper` = now at its start; windows walk newest → oldest. A window is `max_created = win_hi` (+ `min_created = win_lo` once narrowed) paged with `offset += 100` until `offset ≥ count`. The first request of every window is open-ended downwards; if its `count` exceeds `windowCap` (default `REVIEW_WINDOW_CAP` = 12000 + 100, the v3 offset cap) the window is narrowed to `[win_hi − win_span, win_hi]` (first span 90 days, then halved while still too big, doubled after a sparse window; never below 1 h — such a window is paged up to the cap). A finished narrowed window continues with `win_hi = win_lo` (open-ended again); an open-ended window that finishes (or one reaching 946684800) completes the backfill. Windows lie entirely in the past, so their sets only move when Etsy deletes/hides a review or indexes one late; `pageStep` compares every page's `count` with the window's previous one (`win_count`/`inc_count`, persisted, so across runs too): a drop of d steps the offset back by d (a removal before the offset shifts unread reviews below it, whatever the order; re-reads are deduped), a rise just pages on to the new count. A finished window whose `count` (≤ the cap) exceeds the reviews stored in its range (`countReviewsCreated`) is paged again — up to `REVIEW_MAX_REPASS` (2) extra passes per run, while a pass still finds missing ones — which repairs an **unstable order of same-second reviews** across page boundaries. So correctness doesn't depend on the result order (unverified live; the tests run desc, asc, a stable shuffle and `unstable` — ties reordered on every request). Reviews deleted on Etsy are **not** removed from the db (counts never go down). Adjacent windows share their boundary second because the OAS doesn't say whether the bounds are inclusive (dupes are deduped by key; only "both exclusive" would miss a review exactly on a boundary). A shop with ≤ 12 100 reviews needs no narrowing at all.
- **Incremental:** `[synced_through − overlap (7 days), now]` (fixed for the pass: `inc_lo`/`inc_target`), paged; a window too big for the cap is split into its older half first. When the pass completes, `synced_through = inc_target`. The overlap re-reads recent reviews to catch edits and late-indexed ones.
- **Upsert:** an unseen key is inserted (`origin`, `first_seen_scan_id` = the run's scan — the triggering scan, else the latest ok one); a known key gets every column + `raw_json` + `last_seen_at` refreshed and `changed_at` when rating/text/language/photo/update time/listing changed; a changed photo URL requeues the photo; a photo the API stops returning (buyer privacy) → URL NULL, and the image sync deletes the object — we keep only what the API returns.
- **New vs. backfilled:** only rows inserted by an **incremental** pass can be `new`, and while the backfill is incomplete only those created after `backfill_upper` (older ones are still the backfill's territory). Backfilled reviews are never new. "Нові відгуки" = `listNewReviews(latest ok scan)`; `Listing.reviewsNew` ("+N") = the listing's reviews with `origin = 'new'` attributed to the latest ok scan, so it is 0 again after a scan whose sync found nothing.
- **Partial counts:** while `backfill_complete = 0`, `Listing.reviewsPartial` is true and `listing_review_stats.complete = 0` — the UI writes "≥ N".
- **Quota cost:** one request per 100 reviews of history, once (SimplyOrganizedPro ≈ 9 300 reviews → ≈ 94 requests), plus a few narrowing probes for shops above 12 100; afterwards every scan's incremental pass costs **⌈reviews created in [synced_through − 7 days, now] / 100⌉** — the whole overlap is re-read each time, even scans an hour apart: ≈ 1 for SimplyOrganizedPro, ≈ 13 for a shop with ~180 reviews/day. Each run spends at most `budget` = `REVIEW_REQUEST_BUDGET` (300) requests and stops early when `x-remaining-today` < `REVIEW_QUOTA_RESERVE` (1000; the note is shown as the shop's review error) — a 100k-review shop backfills over ≈ 4 scans.
- **When it runs:** after every ok scan (scan:shop, scanAll) — **the UI has one button for everything, "Сканувати повторно"** (no separate review/photo sync buttons any more) — and on the IPC `reviews:sync` (kept, no UI; it returns nothing: the run starts a microtask later, so a state returned there would be the previous run's and could overwrite the new run's first event) — never on app start. `onDone` (index.ts → `onReviewSyncDone`) queues the image sync for the shop (review photos) and sends `shops:changed`. Progress: `reviews:progress` (`ReviewSyncState`: phase, stored, estimate, requests, newReviews, backfillComplete, budgetExhausted, error) after every page.

### Security

- All Etsy calls from main; the renderer has no API key, no MinIO credentials and no network access other than images.
- Renderer runs with `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`. The preload must import nothing but `electron` at runtime (type-only imports are fine) — `tests/main/preload.test.ts` enforces it.
- CSP (`src/renderer/index.html`): `img-src 'self' data: etsyimg: https://i.etsystatic.com https://*.etsystatic.com` (listing photos via `etsyimg:`, shop icons still straight from the CDN); scripts self only; no `connect-src`.
- `setWindowOpenHandler` → deny; `will-navigate` is blocked; external links go through `shell:openExternal`, which only opens `https://` URLs on `etsy.com` / `*.etsy.com` (`shared/externalUrl.ts`).
- Descriptions are rendered as plain text (`white-space: pre-wrap`) — never `dangerouslySetInnerHTML`.
- Etsy sign-in: PKCE + `state` (a pasted URL from another attempt is refused), tokens sealed in settings.json and never sent to the renderer, scopes limited to listings/shop read+write; own-shop writes validated in main before any request.
- The MCP server (off by default) listens on 127.0.0.1 only, behind a random 256-bit bearer token (sealed in settings.json), refuses foreign `Host`/`Origin` headers, and only reads.
- Etsy API terms: listing data shown should be ≤ 6 h old (`isStale` → a banner suggests rescanning); the required trademark notice is in the footer and Settings → "Про програму". Since v2 listing images are **copied** into the user's local MinIO at the user's request (previously only hotlinked) — Etsy's API terms restrict caching/storing content, so keep this a private, local copy (switchable off in Settings → MinIO; then everything is served from the CDN again).

### Drafts in the app — `drafts.ts`, `DraftsModal.tsx`, MCP `prepare_product`

What: a listing is prepared **inside the app** first — by the user ("＋ Новий лістинг" / "📝 Чернетки" in the own shop's header) or by Claude over MCP (`prepare_product`) — reviewed and edited there, and only then sent to Etsy (as an Etsy draft, or published). Every app-side creation goes through a draft (the old direct `myShop:createListing` channel is gone).

**Link model (v6):** a sent draft stays **linked** to its Etsy listing (`sent_listing_id` is the link) — edit it in the app and "Оновити на Etsy" updates *the same* listing (texts, price/quantity, photos, files; publish again if needed). Drafts made on Etsy's site are **pulled** into the app after every ok scan of the own shop (and on "Синхронізувати з Etsy" / MCP `sync_prepared_products`). A draft can be deleted in the app only, or **on Etsy too** (DELETE /listings/{id}). A listing deleted on Etsy leaves its draft marked "видалено на Etsy"; "Надіслати як новий товар" unlinks it and creates a new one.

- **Storage** (`drafts.ts`, schema v5): `saveDraft(db, {id?, source, fields, photos?, files?}, now)` — fields through `normalizeDraftFields` (shared; any stored shape → complete `DraftFields`), media as the full ordered list per kind (`{mediaId}` = keep a stored one of **this** draft (another draft's id is refused), `{name, data}` = new bytes; stored ones not listed are deleted; `undefined` keeps that kind as is), limits/photo types checked before anything is written (one transaction), saving clears `last_error`; the creator (`source`) is kept on updates. A **linked draft is editable** (v6): any save sets `dirty`; kept media keep their `etsy_id`. Slots may also be `{name, data, etsyId}` and `{remote: true, name, size, etsyId}` (files only), and `link: {listingId, state, etsyUpdatedAt}` / `imported` mark a pulled draft as in sync (draftImport.ts). `listDrafts` (newest `updated_at` first, without the BLOBs), `getDraft`, `getDraftByListing`, `getDraftMediaData`, `getDraftMediaEtsyIds`/`setDraftMediaEtsyId`, `deleteDraft` (local only, media cascade). `ListingDraft.status` = `error` (last_error) / `changed` (linked + dirty) / `sent` (linked, in sync) / `draft`; `ListingDraft.etsy` = `{listingId, state, url (active only), editUrl, dirty, syncedAt, etsyUpdatedAt, changedOnEtsy, removed}` | null; `DraftMedia.onEtsy`/`remote`; `problems` = `newListingProblems` for sending as an Etsy draft (`draftProblems`).

### Statistics view (`src/main/shopStats.ts`, `StatsModal.tsx`, `Charts.tsx`, `chartScale.ts`)

IPC `stats:shop` `{shopId, range}` (`range` ∈ `STATS_RANGES` = `all|90d|30d|7d`, anything else → `all` via `parseStatsRange`; a shop id that isn't a positive safe integer, or an unknown shop → `null`) → `shopStatsPayload(db, shopId, range, now)` → `ShopStatsPayload` (shared/types.ts), computed in main so the renderer gets a few hundred numbers, never raw rows:
- `scans` (`statsScans`): every **ok** scan with `finished_at ≥ rangeStart` (error/running never), ordered by `finished_at` (not id), with the scan totals, its `shop_stats` (null fields when the scan has none — scans before v2) and the sums of its `listing_stats` (`listingViews`/`listingFavorers`; null when it has no rows; NULL values are left out of the sum).
- `anchor` (`statsAnchor`): for 90/30/7 days, the latest ok scan **before** `rangeStart` (null for "Усе" or when the period has no scan of its own). It is the period's starting point: `intervals`, `salesRate` and `top` are computed over `[anchor, ...scans]`, and the renderer's KPI Δ and scan lines start there too — so a period's change covers the whole period, and a shop scanned weekly still has a 7-day change. Not in `scans` (the header count, the changes chart).
- each scan point also has `discounted` (listings with `has_discount = 1` in its `listing_price_stats`) and `buyerPriced` (rows with a buyer country); both null when the scan learned no buyer price (pre-v4, refused) → the "Товарів зі знижкою" card (`NO_BUYER_PRICES_HINT` when no scan knows it).
- `intervals` (`statsIntervals`): consecutive-scan deltas (sold, favorers, reviews, views; null when either side is unknown) + `days`.
- `salesRate` (`statsSalesRate`): Δ `transaction_sold_count` / days between scans that know it, **at least `STATS_MIN_RATE_MS` (1 h) apart** — a scan closer than that to the previous anchor is skipped and its gap merges into the next interval, so scans minutes apart can't turn one sale into "300/день"; trailing scans less than that after the last interval's end extend that interval (the intervals always add up to last − first; no interval at all only when every scan is within 1 h of the first). Derived, and labelled so in the UI.
- `reviews` (`reviewBuckets`, from the `reviews` table — the whole history, independent of scans; empty with `synced: false` while `review_sync.backfill_upper` is NULL): `total`/`avg` in the period and zero-filled `weeks` (Monday 00:00 **UTC**, `weekStart`) and `months` (the 1st 00:00 UTC, `monthStart`) — `start`/`end` in Etsy seconds, `count`, `avg`, `ratings[1..5]`, `partial` (the period cuts into the bucket, or it isn't over yet). UTC on purpose: buckets don't depend on the machine's time zone/DST (tested by switching `process.env.TZ`); the renderer formats their labels with `utc = true`. Scan times are shown in local time. Review queries filter on `created_timestamp` alone (`mapReview` already fills it from either OAS spelling), so they use `reviews_shop_created` — never a `COALESCE` there. Never `Math.min(...rows)`/spreads over review rows: a 150k-review shop overflows the stack (tested).
- `top` (`statsTop`): views/favorers growth over the period's scans that have `listing_stats` (the anchor included) up to the last one: each listing starts at **its own first value** among those scans (a listing missing at the first scan — returned or new — still counts), or at **0** when Etsy created it (`original_created_at`, else `etsy_created_at`) after the first scan; growth only, `delta DESC, end DESC, listing_id`, `STATS_TOP_N` = 10, a sparkline value per such scan, `seriesAt` = those scans' times (the sparklines are on a time axis). Plus the most-reviewed listings of the period from the reviews table (`start` = reviews before it, sparkline = `STATS_SPARK_SLICES` equal time slices; empty while never synced). Titles/first image from `listings`/`listing_images` (`Товар #id` and `stored: false` for a listing we never stored — such a row is not clickable).

Renderer: "📊 Статистика" in the shop header → `store.openStats(shopId)` (`statsShopId`) → `StatsModal` (a near-full-width modal rendered by `App` before `HistoryModal`/`ListingModal`, so a listing opened from it sits on top and Escape closes the listing first — chosen over a tab so the shop view keeps its scroll/filters and the existing modal stack is reused). `StatsModal` mounts `StatsDialog` with `key={shop.id}` only while open, so **every opening starts on "Усе"** with no data of the previous shop. Period control (Усе / 90 / 30 / 7 днів, component state, refetches; also when the shop's `lastOkScan`/review sync changes; a refetch keeps the previous render dimmed; a rejected fetch shows "Не вдалося завантажити статистику."), KPI row (latest value + Δ over the period, from the anchor when there is one; the Δ's tooltip names the two scans; 6 tiles, else even rows of 3 or 2 via a container query on `.stats-body`), cards: Продажі магазину (+ "Продажі за день": each rate bar spans its whole interval, so its area is the sales count), Відгуки по тижнях/місяцях (bars + an avg-rating line below — two charts, never a dual axis; auto months above `MAX_AUTO_WEEKS` = 120, switchable; a partial bucket is a dashed outline bar, a dashed line segment with a hollow dot and no end label, with a legend entry and a "* неповний …" table footnote), Обране магазину, Активних товарів, Відгуки магазину (count + average), Перегляди і обране всіх товарів, Зміни за сканування (stack added/removed/changed/returned in one column width, every scan a dot on the axis — baseline scans a ring — so a scan without changes is visible), Топ товарів за ростом (three tables, click → `getListing` → `ListingModal`). Empty states: "У цьому періоді немає успішних сканувань.", `NEED_TWO_SCANS` "Потрібно щонайменше 2 сканування" (+ "з інтервалом щонайменше 1 год" / "зі статистикою товарів"; a scan line with one known point shows "… — зараз: value (date)" instead of a one-dot chart), "…починаючи з версії 2…" for scans without stats, "Відгуки ще не синхронізовано.".
