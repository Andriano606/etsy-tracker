# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Linux desktop app (Electron + React + TypeScript) that **watches Etsy shops** through the **official Etsy Open API v3**. You paste links to Etsy shops; the app reads every active listing of each shop — **everything the API returns** (content, popularity: views / favorers / featured rank, images, videos, personalization; the full JSON is kept too) — stores it in a local SQLite database, copies listing photos into a local **MinIO** bucket (`docker-compose.yml`), and on every rescan ("Сканувати повторно") tells you which listings are **new since the previous scan** — plus which disappeared, came back, or changed (and *what* changed: price, title, description, photos, tags, …), and how popularity grew. The user's own Etsy API key (keystring + shared secret) is entered in the app's Settings. The UI language is Ukrainian; code and comments are English.

The stack, layout and look mirror `/home/andrii/Documents/conductor-linux` (same electron-vite / Vitest / tsconfig shapes, same dark design tokens and IBM Plex fonts, same `.claude/skills`).

## Architecture

Three Electron processes, each a separate electron-vite build target (`electron.vite.config.ts`). Types shared via `src/shared/types.ts`; the renderer imports `src/shared/*` through the `@shared` alias (main/preload use relative `../shared/...`).

- **main** (`src/main/`) — Node side. Owns the database, the API key, and **all** Etsy traffic. Pure functions per concern, wired together in `ipc.ts`:
  - `db.ts` — `node:sqlite` schema, migrations, row mapping, queries. Every function takes the `Db` handle.
  - `etsyApi.ts` — the HTTP client (`createEtsyClient`), errors, quota/Retry-After parsing.
  - `mapEtsy.ts` — Etsy JSON → our records (`mapListing(page, details, currency, includes)`, `mapListingDetails`, `mapImage(s)`, `mapVideos`, `mapPersonalization`, `mapShop` + `mapShopProfile`, `listingStats`, `shopStats`).
  - `scanner.ts` — scan orchestration + the pure diff (`diffListings`, `trackedDiff`, `applyScan`).
  - `imageStore.ts` — the `ImageStore` interface (ensureBucket/ping/put/stat/get/remove), the MinIO implementation (`createMinioImageStore`, official `minio` npm client), object keys, Ukrainian error texts.
  - `imageSync.ts` — `createImageSyncer`: the background Etsy CDN → MinIO copier (`downloadImage` with timeout/retry).
  - `imageProtocol.ts` — the `etsyimg://` protocol handler (MinIO copy, else the CDN) + the pure `resolveImageSource`.
  - `shops.ts` — `addShop` (parse link → `findShops` → insert).
  - `settings.ts` — API-key store (`createKeyStore`) and MinIO settings store (`createMinioSettingsStore`, `MINIO_DEFAULTS`), both with injectable safeStorage, sharing `settings.json`.
  - `ipc.ts` — `registerIpc(ctx)` + `testKey`, `scanAll`, `startImageSync`, `testMinio`, `mergeMinioConfig`; `index.ts` builds the context (db path, key + MinIO stores, client, scanner, cached `getStore`, image syncer, `etsyimg` protocol) and the window.
- **preload** (`src/preload/index.ts`) — a single typed `window.api` over `contextBridge` (sandbox on, contextIsolation on, nodeIntegration off). The `Api` type is derived from this object (`src/renderer/src/env.d.ts`).
- **renderer** (`src/renderer/src/`) — React 18 + one `zustand` store (`store.ts`). No Node access, no network except images (listing photos via `etsyimg://`, built by `imageUrl.ts`; shop icons from the CDN); everything goes through `window.api`.
- **shared** (`src/shared/`) — `types.ts`, `shopUrl.ts` (link parser), `html.ts` (entity decoding), `format.ts` (price/date/staleness/counts/deltas), `externalUrl.ts` (which URLs may open in the browser), `changes.ts` (change-field groups + Ukrainian labels, enum labels).

### Database (`src/main/db.ts`)

Built-in **`node:sqlite`** (`DatabaseSync`) — works in Electron 38 and in system Node 22, so there are no native modules and tests use a real SQLite (`openDb(':memory:')`). The module is loaded lazily via `process.getBuiltinModule('node:sqlite')` inside `loadSqlite()`, which temporarily wraps `process.emitWarning` to swallow only the one-time "SQLite is an experimental feature" ExperimentalWarning (a top-level import would be hoisted above any filter in the CJS bundle). Only `import type` from `node:sqlite` elsewhere.

File: `<userData>/etsy-tracker.db` (WAL, `foreign_keys = ON`). `userData` is pinned in `index.ts` to `~/.config/etsy-tracker` (same for dev and packaged builds, independent of productName). `index.ts` also pins `app.setName('etsy-tracker')` (package.json has no `productName`, and electron-builder's `productName` is not written into the packaged package.json): Linux safeStorage names its keyring secret after the app name and X11 uses it as WM_CLASS, which `scripts/install-desktop.sh` matches with `StartupWMClass=etsy-tracker`.

**Migrations:** `MIGRATIONS` is an append-only array of SQL strings; `PRAGMA user_version` holds how many have run. `migrate(db, migrations = MIGRATIONS)` applies each pending one in its own transaction (a failing one rolls back and leaves `user_version` unchanged — tested with an injected list) and refuses a db whose version is newer than the app knows — so once a v2 build has opened the user's DB, an older installed AppImage refuses it ("створена новішою версією") until it is rebuilt. Never edit a shipped entry — add a new one (and a test in `tests/main/db.test.ts`, starting from a real database at the previous version).

Schema (v2 = `MIGRATIONS.length`; v1 is the first entry, v2 the second — never edit either):
- `shops` — v1: `id` = Etsy `shop_id` (PK), `shop_name` (UNIQUE, NOCASE), `title`, `url`, `icon_url`, `currency`, `etsy_active_count`, `added_at`. v2 adds every useful OAS `Shop` field: `user_id`, `login_name`, `announcement`, `sale_message`, `digital_sale_message`, `is_vacation`, `vacation_message`, `vacation_autoreply`, `num_favorers`, `transaction_sold_count`, `review_count`, `review_average` (REAL), `digital_listing_count`, `accepts_custom_requests`, `languages` (JSON), `shop_location_country_iso`, `shipping_from_country_iso`, `banner_url` (image_url_760x100), `policy_*` (welcome/payment/shipping/refunds/additional/seller_info/privacy) + `policy_updated_at`, `etsy_created_at`/`etsy_updated_at` (seconds), `raw_json` (the whole GET /shops/{id}), `info_fetched_at` (ms; NULL = never read with v2 → `Shop.profile` null).
- `listings` — v1: `listing_id` (Etsy id, PK), `shop_id` (FK cascade), `title`, `description` (HTML entities already decoded), `price_amount` + `price_divisor` + `currency` (Etsy `Money` kept exactly: value = amount / divisor, no floats), `url`, `tags` (JSON), `quantity`, `etsy_created_at` / `etsy_updated_at` (Etsy epoch **seconds**), `first_seen_at`, `last_seen_at`, `removed_at` (our epoch **ms**; `removed_at IS NULL` = active). Rows are never deleted when a listing disappears — only marked. v2 **drops** the v1 `images` JSON column (moved to `listing_images`) and adds every scalar of OAS `ShopListingWithAssociations`: `user_id`, `state`, `views`, `num_favorers`, `featured_rank`, `shop_section_id`, `taxonomy_id`, `listing_type`, `who_made`, `when_made`, `is_supply`, `materials`/`style`/`skus` (JSON), `processing_min/max`, `is_customizable`, `is_personalizable`, `personalization` (JSON `PersonalizationQuestion[]` from `includes=Personalization`), `has_variations`, `is_private`, `is_taxable`, `non_taxable`, `should_auto_renew`, `file_data`, `language`, `shipping_profile_id`, `return_policy_id`, `readiness_state_id`, `item_weight` + unit, `item_length/width/height` + `item_dimensions_unit`, `original_created_at`, `ending_at`, `state_at` (seconds), `raw_json` (the latest full API object — details if fetched; the page item only when nothing is stored yet), `details_fetched_at` (ms; NULL = row from v1 → `Listing.details` is null). Booleans are 0/1/NULL. There is no `is_digital` in the OAS — `listing_type` (`physical|download|both`) says it. Associations not requested (Shop, User, Translations, BuyerPrice, Inventory) are not stored; anything else in the response is in `raw_json`.
- `listing_images` (v2) — one row per (`listing_id`, `listing_image_id`) (composite PK; index on `listing_image_id`) — live Etsy **reuses one image id on several listings** of a shop (44 of 448 photos in the test shop), so the image id alone is not a key — with **every** ListingImage field (`listing_id` FK cascade, `shop_id`, `rank`, `url_75x75/170x135/570xN/fullxfull`, `full_width/height`, `hex_code`, `red/green/blue`, `hue/saturation/brightness`, `is_black_and_white`, `alt_text`, `created_timestamp`), `first_seen_at`, `removed_at` (ms; set when the id leaves the listing), and the MinIO state: `sync_status` `pending|stored|error`, `sync_error`, `sync_attempts`, `stored_at`, `key_full`/`key_570` (object keys; NULL = no object), `byte_size`, `content_type`, `etag`, `sha256` (of the fullxfull bytes). Migration v2 backfills it from the v1 JSON (`json_each`, corrupt JSON skipped) as `pending`. `Listing.images` = the active rows by rank.
- `listing_videos` (v2) — PK (`listing_id`, `video_id`) (videos are shared across listings too), `width`, `height`, `thumbnail_url`, `video_url`, `video_state`, `first_seen_at`, `removed_at`. Metadata only — videos are not copied to MinIO.
- `listing_stats` (v2) — `(scan_id, listing_id)` PK: `views`, `num_favorers`, `featured_rank`, `quantity` per successful scan (baseline included); when a scan didn't learn the views (no details answer, or a distrusted 0) the listing's kept value is carried into that row so the history and deltas stay continuous. Read by `listListingStats` → IPC `listing:stats` → "Історія популярності" in `ListingModal`. `shop_stats` (v2) — `scan_id` PK, `shop_id`, `num_favorers`, `transaction_sold_count`, `review_count`, `review_average`, `listing_active_count`. Both cascade with `scans`. Growth = latest − previous successful scan: `Listing.favorersDelta`/`viewsDelta` (listing column vs. the second-latest ok scan's `listing_stats`) and `ShopSummary.stats`/`statsDelta`; null when there is no previous value.
- `scans` — `status` `running|ok|error`, `error`, `is_baseline`, `truncated`, totals `total/added/removed/changed/returned`.
- `scan_changes` — `(scan_id, listing_id, kind, old_value, new_value)`; kind `added|removed|changed|returned`; old/new are JSON `TrackedFields` holding only the changed fields (see "changed" below). v1 rows (title/price only) read the same way.

`upsertListing` with `images: null` / `videos: null` keeps the stored ones (the details call didn't answer for that listing); an array is synced into `listing_images`/`listing_videos` (`syncListingImages`: new id → `pending`; known id → metadata refreshed, a changed `url_fullxfull`/`url_570xN` resets it to `pending`; missing id → `removed_at`; a returning id is revived). `skus` and `details_fetched_at` are only overwritten when `detailsFetched`; `personalization` only when `personalizationFetched` (defaults to `detailsFetched`; `mapListing` sets it only when the details object has the key or `Personalization` was among `client.detailIncludes()` — after the Images-only fallback the stored questions are kept and not diffed); `views` is `COALESCE`d (null = unknown → keep); `raw_json` from details replaces the stored one, a page-only object never does. `deleteShop` removes the shop's listings, images, videos, scans, stats and changes in one transaction (MinIO objects: collect `listShopObjectKeys` first — `shop:remove` does, then `images.removeObjects`).

### Etsy API client (`src/main/etsyApi.ts`)

- Base `https://openapi.etsy.com`, paths `/v3/application/...`. Header on **every** request: `x-api-key: <keystring>:<shared_secret>` — since 2026-02-09 Etsy rejects the keystring alone, so the app asks for both halves (`composeApiKey` in `settings.ts`). No OAuth: only public endpoints are used.
- Endpoints: `GET /openapi-ping` (key check → `{application_id}`), `GET /shops?shop_name=&limit=100[&offset=]` (findShops — a name *search*, may be fuzzy, so we keep only an exact case-insensitive `shop_name` match and page on, up to `FIND_SHOP_MAX_PAGES` = 5, while it isn't found and `count` says there is more; no match is `count: 0`, not 404), `GET /shops/{id}`, `GET /shops/{id}/listings/active` (paginated, **no `includes`** → no images), `GET /listings/batch?listing_ids=1,2,3&includes=Images,Videos,Personalization` (≤100 ids, comma-separated, no brackets), `GET /listings/{id}?includes=…` (`getListing`, null on 404). `includes` (`DETAIL_INCLUDES`): the OAS enum is Images, Shop, User, Translations, Videos, Personalization, BuyerPrice — Shop/User duplicate what we read, Translations multiply the payload, BuyerPrice is buyer-specific, so they aren't requested. If Etsy answers 401/403 to the full set while `Images` alone works, the client falls back to `Images` for the rest of its life (`detailIncludes()`), so an include that needs OAuth can never break scans. `views` is documented only in `ShopListingWithAssociations` (Etsy tabulates it once a day), but live the `/listings/active` page items carry it too (same value; also `skus`, `production_partners`) — `mapListing` falls back to the page's `views` when details didn't answer. Details are still fetched for every listing for images/videos/personalization. Never `GET /shops/{id}/listings` — it needs OAuth `listings_r`.
- **Batch 404s:** the OAS documents a 404 for `/listings/batch` (likely when an id is unknown — deleted / no longer public; unverified live). `getListingsByIds` therefore bisects a chunk answered 404 or 400 down to single `GET /listings/{id}` calls; a single-id 404 means "gone" (left out of the result), any other error still throws. Without this, a deleted listing would make every rescan of its shop fail forever.
- Paging caps: `limit` ≤ 100, `offset` ≤ 12000 → at most ≈12,100 listings per shop. `getAllActiveListings` loops `offset += 100` until `offset >= count`, an empty page, or past the cap; dedupes by `listing_id`; sets `truncated` when `count > 12100`.
- Requests are serialized through one promise chain with a minimum gap (`minIntervalMs`, default 125 ms). 429 → wait `Retry-After` (seconds or HTTP date) + jitter, else exponential backoff; a `Retry-After` beyond `maxRetryAfterMs` (60 s — the daily quota) fails fast. 5xx and network errors → backoff retry. Up to `maxRetries` (4). Every attempt has a timeout (`requestTimeoutMs`, default 30 s, via `AbortController` covering headers and body); a timeout is retried at most `maxTimeoutRetries` (1) times, then fails as a `network` error "Etsy не відповідає (тайм-аут 30 с)…" — so a stalled connection can't block the serialized queue (ping, findShops, other scans) for minutes. 401/403 → `auth`, 404 → `not_found`, 400 → `bad_request`; each `EtsyApiError` carries a Ukrainian `message`, `kind`, `status`, Etsy's `{"error"}` text as `detail` and `x-etsy-request-uuid` as `requestId`.
- Quota: `x-limit-per-day`, `x-remaining-today`, `x-limit-per-second`, `x-remaining-this-second` are parsed from every response (`parseQuota`) and pushed to the renderer (`quota:changed`, shown in the sidebar footer). Limits are per key and are never hardcoded.
- `fetch`, `sleep`, `random`, `now` are injectable — tests run against a fake Etsy, never the network.
- Verified live (2026-10, real key, SimplyOrganizedPro): `Videos`/`Personalization` includes work with API-key-only auth; a listing without personalization has `personalization: {personalization_questions: []}`; the quota headers are `x-limit-per-day`/`x-remaining-today`/`x-limit-per-second`/`x-remaining-this-second`; batch/page/shop responses match the fixtures except extra live-only keys (`rich_description`; on pages `views`, `skus`, `production_partners`, `suggested_title`, `ecgt_*`) — kept in `raw_json`; `featured_rank` values seen: -1, 0, 1, 2, 3 (the UI shows ★ only for ≥ 1).
- UNVERIFIED API details are coded defensively: entity decoding of title/description/tags (`shared/html.ts`), fuzzy findShops, what `/listings/batch` does with unknown ids (skip vs 404), whether a Seller-App key can read other shops.

### Scan & diff semantics (`src/main/scanner.ts`)

`createScanner({db, client, now, onProgress}).scanShop(shopId)`:
1. Refuses if that shop is already scanning (`busy`), inserts a `running` scan row.
2. `getShop` (refreshes title/icon/count + the full profile and shop stats; a vanished shop → 404 error), then pages all active listings.
3. Fetches details via the batch endpoint for **every** active listing on every scan (images/videos/personalization exist only there). **Cost per scan ≈ 1 (getShop) + ⌈N/100⌉ (pages) + ⌈N/100⌉ (details) requests** (+ the removal re-check), i.e. ~2 requests per 100 listings — v1 skipped unchanged listings, v2 can't. A listing deleted between paging and this call (404) is still saved from its page data, keeping its stored images/views.
4. Listings stored as active but missing from the pages are **re-checked** through the batch endpoint (they may just have shifted between pages); only those not `state: 'active'` in this shop — or unknown to Etsy (404) — count as removed. When the set was `truncated`, removal detection (and this re-check) is skipped entirely and the scan row gets `truncated = 1` (UI warns "≈12 100").
5. One transaction (`applyScan`): update shop info + profile + raw JSON, upsert every current listing (columns, raw JSON, `listing_images`, `listing_videos`), mark removed ones, insert `scan_changes`, write `listing_stats` for every current listing and `shop_stats` (baseline included), finish the scan row `ok` with totals.
6. **Not** part of the scan: copying images to MinIO. After an ok scan, `ipc.ts` calls `startImageSync(ctx, shopId)` (fire-and-forget) — see "Image store".

Rules:
- **Baseline:** a shop's first successful scan (`!hasOkScan`) saves everything (and stats) but records no changes (`is_baseline = 1`, counts 0). UI: "Базове сканування: збережено N товарів".
- **added** = `listing_id` never seen before; **returned** = stored with `removed_at` and active again (its own kind — not counted as new, no NEW badge, shown in a separate "Повернулися" group); **removed** = active before, gone now; **changed** = content differs (`trackedDiff`):
  - always: title, price (by value: `a1*d2 != a2*d1`, or a currency change), description (old/new stored as ≤ 1000-char excerpts, `DESCRIPTION_EXCERPT`), tags (as a set);
  - images: the ordered list of active `listing_image_id`s (new/replaced/removed photo or a new order), only when this scan fetched images and the stored row had images (or v2 details);
  - only when the stored row already has v2 details (so the first v2 rescan of a v1 row can't flag everything): materials and styles (sets), `whoMade`, `whenMade`, `taxonomyId`, `shopSectionId`, `listingType`, `isPersonalizable`, `isCustomizable`, `hasVariations`, processing time (`processingMin`+`processingMax` together), weight/dimensions (one `dimensions` string), personalization questions (only a known previous value vs. a fresh answer — `personalizationFetched`), video ids;
  - **views 0:** the OAS says a `views` of 0 may mean "not yet tabulated / not active at tabulation / error"; `distrustZeroViews` turns a 0 for a listing whose stored views were > 0 into null (unknown → kept, no negative delta). A new listing's 0 is stored.
  - **never a change**: views, favorers, featured rank (popularity) and `quantity` (stock moves with every sale) — they're recorded per scan in `listing_stats` instead. A changed image URL with the same id isn't a content change either (it only resets that image to `pending`).
  - The row's `new_value` keys say what changed; `shared/changes.ts` maps them to groups/labels ("ціна, опис, фото").
- **Failure:** all Etsy API I/O happens before the transaction, so any error (network, 429 exhaustion, API error mid-pagination or mid-details) leaves listings, images and stats untouched and only marks the scan row `error` with the Ukrainian message. The shop summary then has `lastScan` (failed) ≠ `lastOkScan`, and the UI shows the error above the previous results.
- Scans left `running` by a crash are closed as `error` when the scanner is created (`failStaleRunningScans`).
- `scanAll` (ipc.ts) scans shops sequentially, starts the image sync after each ok shop, and stops early on an API-key error.
- Progress events (`scan:progress`): `Сторінка 2/5`, `Деталі 100/430`, `Перевірка зниклих …`, `Збереження…`; `scan:state` brackets each scan.

### Image store (MinIO) — `imageStore.ts`, `imageSync.ts`, `imageProtocol.ts`

- **Container:** `docker-compose.yml` (project `etsy-tracker`): service `minio`, image `${MINIO_IMAGE:-minio/minio:RELEASE.2025-09-07T16-13-09Z}`, `127.0.0.1:9100→9000` (S3 API) and `127.0.0.1:9101→9001` (console) — host 9000 is taken on this machine; credentials `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD` from `.env` (defaults `etsytracker` / `etsytracker-minio-secret`, see `.env.example`; `.env` is gitignored — the default password is public, so Settings shows a warning while `secretSource === 'default'`), `MINIO_API_CORS_ALLOW_ORIGIN` = `${MINIO_CORS_ALLOW_ORIGIN:-http://127.0.0.1:9101}` (MinIO's default CORS answers any origin, which would let any web page in the user's browser call the S3 API with the known credentials; verified live that a foreign origin then gets no `Access-Control-Allow-Origin`), `tests/main/settings.test.ts` checks `MINIO_DEFAULTS` against the compose file and `.env.example`, named volume `minio-data`, curl healthcheck on `/minio/health/live`, `restart: unless-stopped`. MinIO Inc. stopped publishing community images to Docker Hub in late 2025 (`minio/minio` pulls are "access denied"); the pinned tag works where the image is cached (on this machine it was tagged from the cached `minio/minio:latest`, which is that release); elsewhere set `MINIO_IMAGE` (e.g. the `pgsty/minio` community build). No `mc` init service: the app creates the bucket (idempotent `ensureBucket`).
- **Settings** (`createMinioSettingsStore`, same `settings.json` as the API key): `minio: {enabled, endpoint, accessKey, bucket, secretKey: {data, encrypted}}` — the secret sealed with safeStorage like the API key. Nothing saved = `MINIO_DEFAULTS` (enabled, `http://127.0.0.1:9100`, the compose credentials, bucket `etsy-tracker`), so it works out of the box with `docker compose up -d`. The renderer only gets `MinioStatus` (`secretSource: 'default'|'stored'`, `encrypted`, `unreadable`) — never the secret; an empty secret on save keeps the stored one. `minio:test` merges typed values over the stored config (`mergeMinioConfig`) and does `ping` (signed `listBuckets`) + `ensureBucket`. Saving drops the cached client (`onMinioChanged`), resets every stored image to `pending` when the endpoint or bucket changed (`resetStoredImages`), and always starts a sync (a disabled store finishes at once with `disabled`, which clears a stale MinIO error in the shop header). The compose file is in the source checkout only — the packaged app doesn't ship it (README has a `docker run` equivalent).
- **Client:** the official `minio` npm package (pure JS, small, has a CJS `require` export) rather than `@aws-sdk/client-s3` (dozens of packages, heavier to bundle). It is a `dependency`, externalized by `externalizeDepsPlugin` (the main bundle does `require("minio")` — keep the import static; a dynamic `import()` would load its ESM build) and shipped by electron-builder from `node_modules`. Every call has a timeout (15 s); errors become `ImageStoreError` with a Ukrainian text (`describeStoreError`: ECONNREFUSED → "MinIO недоступний… docker compose up -d", bad credentials, …).
- **Object keys:** `shops/{shop_id}/listings/{listing_id}/{listing_image_id}/{size}.{ext}`, sizes `fullxfull` (original) and `570xN` (grid thumbnail), ext from the response content-type (else the URL, else jpg), content-type stored on the object.
- **Lifecycle** (`createImageSyncer`): a scan commits `pending` rows; then one background run at a time (requests made while one runs are merged into the next): `getStore()` (null = disabled → state `disabled`) → `ensureBucket` → delete objects of removed images (`listImagesToCleanup` → keys NULL, status back to `pending`) → on a `force` run (the manual "Синхронізувати фото") `stat` the keys of every stored row of that scope and requeue missing ones (`markImageMissing`) → for every active `pending` row and `error` row with < 5 attempts (`force` = all errors), re-read the row (skip it if gone, removed or already stored — the run's list is a snapshot, the shop may have been deleted meanwhile), download fullxfull + 570xN from Etsy's CDN (`downloadImage`: 30 s timeout, 2 retries on 5xx/429/network, no retry on 404, must be `image/*`), upload, record `stored` (+ key, size, content-type, etag, sha256) — only if the row still has the URL that was downloaded (`markImageStored` guard; a rescan may have replaced it or the shop was deleted); when that guard refuses, the just-uploaded objects are deleted so nothing is orphaned. A 570xN that doesn't exist (no URL, 404/410) still stores the original; any other thumbnail failure fails the image (`error`, retried). Cleanup clears the keys with `markImageObjectsDeleted(id, keyFull, key570)`, guarded by the deleted keys rather than `removed_at`, so an image a rescan revived meanwhile goes back to `pending` and is uploaded again. A CDN failure marks that image `error` (attempts+1); a **MinIO** failure (`ImageStoreError`) stops the run and leaves the rest `pending` — never `error`. Concurrency 3. CDN downloads don't count against the API quota. A MinIO outage or a disabled store can never fail or roll back a scan; pending images are retried after the next scan, 5 s after app start, on saving MinIO settings, or via "Синхронізувати фото". Progress goes to the renderer as `images:progress` (`ImageSyncState`, throttled to 250 ms); `images:status(shopId)` gives `ImageCounts`.
- **Display — `etsyimg://img/{listing_image_id}/{size}`** (registered privileged `standard`+`secure` before `ready`, handled with `protocol.handle` in `index.ts`). The handler looks the id up in `listing_images` (`getImageRow(db, id)` without a listing = the best row of a shared image: stored first, then active); every other image function addresses one row by `ImageRef {listing_id, listing_image_id}` (an `ImageRow` is one); `resolveImageSource` (pure, tested): stored + store available → stream the MinIO object (small sizes use the 570xN copy, else the original), else the Etsy CDN URL of the requested size, fetched by main (`net.fetch`) and passed through; a MinIO error at read time also falls back to the CDN; a stored row whose object the store reports missing is also served from the CDN and `onMissing` (index.ts) marks it pending and queues a sync; unknown id → 404, malformed → 400, CDN failure or a non-`image/*` answer → 502. **URL validation:** every image URL from Etsy JSON must pass `isEtsyCdnUrl` (`shared/externalUrl.ts`: `https:` on `etsystatic.com`/`*.etsystatic.com`, no credentials) — `mapImage` stores `''` otherwise, `resolveImageSource`/`fromCdn` and `downloadImage` refuse it — and main's CDN fetch is `net.fetch(url, {bypassCustomProtocolHandlers: true})`, because `net.fetch` would also read `file:` URLs and our own `etsyimg:`. The renderer never sees MinIO credentials or keys (`imageUrl.ts` builds the URL from the image id).

### API-key storage (`src/main/settings.ts`)

`<userData>/settings.json` (mode 0600, atomic tmp+rename; also holds the `minio` section, see above) holds `apiKey: {data, encrypted}` — the full `keystring:secret`, encrypted with Electron `safeStorage` when `isEncryptionAvailable()`, otherwise plaintext. The renderer only ever gets `KeyStatus {hasKey, masked: 'abcd…wxyz', encrypted}`; `encrypted` is false for the Linux `basic_text` backend (hardcoded password) too, and the UI then shows a warning. A stored encrypted key that fails to decrypt (keyring locked/unavailable/changed) gives `{hasKey: false, unreadable: true}` — Settings and the shop view then say "Збережений ключ не вдалося розшифрувати… — введіть ключ ще раз" instead of "Ключ не задано". `key:test` can ping with typed-but-unsaved values or with the stored key.

### Security

- All Etsy calls from main; the renderer has no API key, no MinIO credentials and no network access other than images.
- Renderer runs with `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`. The preload must import nothing but `electron` at runtime (type-only imports are fine) — `tests/main/preload.test.ts` enforces it.
- CSP (`src/renderer/index.html`): `img-src 'self' data: etsyimg: https://i.etsystatic.com https://*.etsystatic.com` (listing photos via `etsyimg:`, shop icons still straight from the CDN); scripts self only; no `connect-src`.
- `setWindowOpenHandler` → deny; `will-navigate` is blocked; external links go through `shell:openExternal`, which only opens `https://` URLs on `etsy.com` / `*.etsy.com` (`shared/externalUrl.ts`).
- Descriptions are rendered as plain text (`white-space: pre-wrap`) — never `dangerouslySetInnerHTML`.
- Etsy API terms: listing data shown should be ≤ 6 h old (`isStale` → a banner suggests rescanning); the required trademark notice is in the footer and Settings → "Про програму". Since v2 listing images are **copied** into the user's local MinIO at the user's request (previously only hotlinked) — Etsy's API terms restrict caching/storing content, so keep this a private, local copy (switchable off in Settings → MinIO; then everything is served from the CDN again).

### UI map (`src/renderer/src/components/`)

- `App.tsx` — layout + event subscriptions; main area: `NoKeyState` (no key and no shops; how-to-get-a-key steps from `KeyHelp`), `NoShopsState`, or `ShopView`; global error banner; trademark footer.
- `Sidebar.tsx` — shop list (icon, name, active count, `+N` new badge, spinner + progress label, "помилка сканування"), "+ Додати магазин", settings gear (red dot without a key), "Сканувати всі", daily quota.
- `ShopView.tsx` — header (icon, name, link to Etsy, last scan time, `ShopStatsLine`: sold / ★ rating (reviews) / ❤ favorers with deltas vs. the previous scan, `ImageSyncLine`: "Фото: stored/total · помилок: N", sync progress, MinIO error/disabled, "Синхронізувати фото"; "Сканувати повторно" / "Видалити" with confirm), banners (no key / failed scan / stale data / never scanned), `ScanResults` (new listings first as cards, then collapsible "Повернулися", "Зникли", "Змінились: N (ціна, опис, фото…)" — every changed row says "Змінилось: …" plus old → new lines), the grid of all active listings with search (title/tags) and sort (`listingFilter.ts`: новіші / ціна ↑ / ціна ↓ / найпопулярніші (обране) / перегляди / ріст обраного — unknown values last), NEW badge on listings added by the latest scan, and `ScanHistory`.
- `ListingCard.tsx` — thumbnail (`etsyimg://…/570xN`), title, price, `PopularityBadges` (❤ favorers + "+N" growth when > 0, 👁 views, ★ featured rank when ≥ 1).
- `ListingModal.tsx` — gallery, price, facts (quantity, ❤/👁 with deltas, featured rank, dates), tags, plain-text description, "Деталі" (`detailRows`: state, materials, style, who/when made, type, processing time, weight, dimensions, personalization + questions, variations, category, section, language, SKUs, …), a collapsible "Історія популярності" table (`listing:stats`, newest first, loaded only when opened), a collapsible raw-JSON viewer (`listing:raw`, loaded only when opened), "Відкрити на Etsy". `HistoryModal` (in `ScanHistory.tsx`) — one past scan's changes grouped by kind.
- `SettingsModal.tsx` — key status (masked), Keystring + Shared secret (password) inputs that always start empty, Зберегти / Перевірити ключ / Видалити ключ; `MinioSection.tsx` "Сховище зображень (MinIO)" (enable toggle, endpoint, access key, secret — empty password input, status says default (a warning: the compose password is public)/stored/encrypted/unreadable — bucket, "Зберегти MinIO", "Перевірити з’єднання"); help, about + trademark notice. `minioStatus` is loaded with the app (`store.load`), not on opening Settings.
- `AddShopModal.tsx` (validates with `parseShopInput` before calling main), `ConfirmModal.tsx` (in-app confirm; native `confirm()` breaks focus on Linux).
- Every modal closes on Escape through `useEscape(onClose, open)` (`components/useEscape.ts`): one document-level keydown listener and a stack, so only the most recently opened modal closes (focus usually stays on the button outside the modal, so a backdrop `onKeyDown` would never fire). `App` renders `HistoryModal` before `ListingModal` so a listing opened from the history sits on top.
- `store.scanAll` resets only the shops it marked as scanning, never one with its own `scanShop` still in flight (main reports each shop done during scanAll, so the user can rescan it meanwhile).

Shop link parsing (`shared/shopUrl.ts`) treats a link as a listing link only when `listing` is the first path segment (after an optional locale) — a shop may be named "Listing". It accepts `etsy.com/shop/Name` with/without scheme/`www`, `http`, `m.etsy.com`, locale prefixes (`/uk/shop/…`, `/en-gb/shop/…`), query/hash, trailing slash, extra path (`/reviews`), `Name.etsy.com`, or a bare name; rejects listing links, non-Etsy hosts, Etsy's own subdomains and names that aren't letters+digits.

## Testing conventions

Vitest, `tests/` mirrors `src/`: `tests/shared/*`, `tests/main/*`, `tests/renderer/*` (+ `components/`). Renderer tests start with `// @vitest-environment jsdom` (default env is `node`); `tests/setup.ts` adds jest-dom and RTL cleanup.

- **Fake Etsy, never the network:** `tests/helpers/fakeEtsy.ts` (`FakeEtsy`) serves the real endpoint shapes over a mutable `listings` array (paging, batch ≤100, `GET /listings/{id}`, 404s) with an `intercept(url, n)` hook for injecting 4xx/5xx/429/network failures; `.client()` returns a client with no-op sleep. Listings (`mkEtsyListing`) are `ShopListingWithAssociations` (two images, `videos: []`, `personalization: null`, `views` = 100+id, `num_favorers` = 10+id); pages strip every `ASSOCIATION_KEYS` key, batch/single attach only the requested `includes` (Images/Videos/Personalization…). `refuseIncludes: ['Videos']` answers 403 when such an include is asked (tests the Images fallback). `batchUnknown: '404'` makes `/listings/batch` fail with 404 when any id is unknown (splice a listing out of `listings` to "delete" it); the default `'skip'` silently leaves unknown ids out. `tests/helpers/fakeFetch.ts` (`fakeFetch`, `queuedFetch`) for request-level client tests. JSON fixtures in `tests/fixtures/` are shaped exactly like Etsy's responses — `shop.json` and `listingWithAssociations.json` carry **every** property of the OAS `Shop` / `ShopListingWithAssociations` schema (in spec order), `listing.json` is a plain `ShopListing`, `listingImage.json` a full `ListingImage`.
- **Fake MinIO and CDN:** `tests/helpers/fakeImageStore.ts` — `FakeImageStore` (in-memory `ImageStore`; `down = true` makes every call throw like an unreachable server, `failPutsAfter = n` simulates a mid-run outage, `removed` records deletions) and `fakeCdn(opts)` (a fetch serving `cdnBytes(url)` as `image/jpeg`; `status: {urlPart: 404}`, `failing: [urlPart]`). The real MinIO client is not unit-tested — verify it live against `docker compose up -d` (a scratch script using `createMinioImageStore`).
- **Real SQLite:** `tests/helpers/db.ts` (`memDb()`, `seedShop`, `mkInput`, `mkListing`, `mkDetails`) — an in-memory `node:sqlite` db per test, no Electron. `mkInput` is a v2 listing (`details: mkDetails()`, `detailsFetched: true`); pass `details: null` for a v1-era row. - **safeStorage mock:** `tests/helpers/safeStorage.ts` (`fakeSafeStorage(available, backend)`); key-store tests use temp files.
